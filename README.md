Define a staging version of an existing Docker Compose application and deploy isolated feature-branch previews through GitHub Actions.

**Status: specification only.** This repository currently documents the intended behavior and an illustrative Compose fragment. It does not yet contain a deployment runner, executable CI workflows, or runtime validation. No deployment has been performed.

## The problem this should solve

A web repository already has a Compose stack containing PHP, a database, and possibly a web server, workers, or Redis. Its staging version should reuse that application while adding phpMyAdmin and Mailpit, applying staging-specific configuration, and keeping each feature branch's data and URLs separate.

Define that variant once, commit it with the application, and instantiate it for each selected feature branch or pull request. A new commit updates the existing preview rather than creating a new database or changing its credentials.

```text
Existing application Compose definition
  + repository-owned staging overlay
  + staging settings and scoped secrets
  + branch identity and tested image references
  = repeatable feature-branch preview
```

This is an environment-definition and lifecycle tool, not merely a release-status checker. Compose remains responsible for describing services. CI remains responsible for tests and image builds. Artifact Release should coordinate the predictable application of the staging definition.

## Define staging in the application repository

Proposed layout; these files are not generated by this repository yet:

```text
compose.yaml                       # Application services
compose.staging.yaml               # Staging changes and additional services
.env.staging.example               # Non-secret defaults and required variable names
.github/workflows/staging.yaml     # CI integration
scripts/staging/                    # Explicit, application-specific lifecycle hooks
```

Prefer native Compose overlays over inventing a second service-definition language. An initial setup step may help prepare the files, but normal deployments must execute the reviewed definition deterministically, not ask an AI to redesign the environment.

Docker supports adding services and overriding existing service settings using multiple `-f` arguments. Always select files explicitly; do not accidentally include a local-development `compose.override.yaml`. Relative paths in overlays resolve against the first Compose file, not against the overlay's directory. [1]

### Example staging changes

The following is an **illustrative fragment, not a complete deployable stack**. It assumes application services named `php` and `db` on the project's default network, with application code that reads the shown variable names. A real definition must additionally wire database credentials, image references, ingress, health checks, and every relevant worker.

```yaml
# compose.staging.yaml
services:
  php:
    environment:
      APP_ENV: staging
      APP_DEBUG: "false"
      APP_URL: "${STAGING_APP_URL:?staging application URL required}"
      DB_HOST: db
      DB_PORT: "3306"
      MAIL_HOST: mailpit
      MAIL_PORT: "1025"

  db:
    # Do not retain a database port published by the base configuration.
    ports: !reset []

  phpmyadmin:
    image: "${PHPMYADMIN_IMAGE:?pinned phpMyAdmin image required}"
    environment:
      PMA_HOST: db
      PMA_PORT: "3306"
      PMA_ABSOLUTE_URI: "${STAGING_DB_UI_URL:?protected database UI URL required}"
    # No host port. Ingress must provide authenticated access.

  mailpit:
    image: "${MAILPIT_IMAGE:?pinned Mailpit image required}"
    # No host ports. PHP sends SMTP to mailpit:1025 internally.
    # Ingress may expose the UI on container port 8025 behind authentication.
```

phpMyAdmin supports `PMA_HOST`, `PMA_PORT`, and `PMA_ABSOLUTE_URI`; do not configure automatic database login with `PMA_USER` and `PMA_PASSWORD` as a convenience default. Mailpit uses SMTP port 1025 and web UI port 8025 by default. Neither database nor SMTP access needs a host-published port for communication on the Compose network. [4][5]

The staging definition must also select the application's SMTP mail transport, remove conflicting mail DSNs and production mail credentials, and disable external mail delivery. Adding Mailpit alone does not reconfigure PHP, Laravel, Drupal, WordPress, or custom application code. Environment names and bootstrap requirements are repository-specific.

## Environment configuration is part of the contract

Staging must explicitly define or bind:

- Application environment, public URL, session/cookie scope, trusted proxy settings, and debug policy.
- Database host, database name, username, and password shared consistently between initialization and application services.
- Mail transport, Mailpit host/port, and any framework-specific authentication or TLS settings.
- Worker, queue, cache, upload/storage, and external integration settings wherever those services exist.
- Sandbox credentials and endpoints for external services. Do not inherit production `.env` files or production secret sets.

Separate non-secret repository defaults, per-environment generated values, and secret-store bindings. Generate database credentials and application encryption keys once per preview; reuse them on subsequent commits. Changing initialization variables is not a database credential-rotation strategy.

Compose's CLI `--env-file` supplies interpolation values; it does **not** automatically inject every variable into every container. Use explicit service `environment`, service `env_file`, or supported secret-file bindings. Account for shell-environment precedence and remove conflicting inherited values rather than assuming a staging env file overrides everything. Never source an untrusted env file as a shell script. [2]

Before deployment, resolve and inspect the effective Compose model without publishing its secrets. Validate that required settings exist and that all application services, including workers, point to the intended staging dependencies. Use application-specific checks to confirm the running code actually consumes those settings. Laravel configuration caches, PHP-FPM environment handling, Drupal settings, or WordPress configuration may require explicit bootstrap hooks.

## One stable preview per branch or pull request

The environment identity must be distinct from the release identity:

```text
Environment: repository ID + PR number (or a validated branch-derived ID)
Release:     exact tested commit + image digests + configuration revision
```

Use an explicit Compose project name such as `ar-r123456-pr42`. Docker documents project names as a way to isolate separate deployments of the same Compose application. [3]

For branch-only deployments, include a short hash of the full ref in the normalized ID to avoid collisions. Do not use raw branch names in shell commands, paths, DNS labels, or project names. Do not include the commit SHA in the persistent environment identity.

Each preview should own its database, credentials, volumes, networks, queues, uploads, and mail inbox. A trusted host-managed ingress layer should assign stable application, database UI, and mail UI URLs. No production databases or shared development volumes.

Project names alone are not sufficient when the base configuration uses explicit `container_name`, globally named volumes/networks, external resources, fixed host ports, host networking, or shared bind-mount paths. Reject unsafe inheritance or require an explicit staging override. Compose merges some lists rather than replacing them: an empty `ports: []` is not a reliable removal mechanism. Use supported `!reset`/`!override` behavior and enforce a compatible Compose version; `!override` requires Compose 2.24.4 or newer. [1][6]

## Intended deployment lifecycle

1. **Select and verify a revision.** Resolve the approved branch/PR event to an exact commit. Run the required tests and build the application images in CI. Record the resulting image digests. When testing a synthetic PR merge commit, deploy that same tested revision rather than silently substituting the branch head.
2. **Resolve the staging definition.** Combine the selected Compose files, explicit settings, scoped secrets, and environment identity. Validate the effective model before changing the host. Application builds in the source definition are fine; the deployed model should use CI-built images without rebuilding them on the staging host.
3. **Serialize environment mutations.** Use a shared lock for deployment and cleanup of the same preview. Re-check that the environment is still desired and the revision is not stale after acquiring the lock. GitHub Actions concurrency is useful, but cancellation and queue ordering must not be treated as a complete host-side lock or stale-release policy. [7]
4. **Prepare dependencies and data.** Start required infrastructure and wait for database readiness. Initialize and optionally seed a new preview once. Run the repository's explicit, idempotent migration/bootstrap hooks against the candidate image. Do not reset the database on every push.
5. **Start and verify the application.** Start application services and workers, wait for meaningful health checks, and run smoke tests. `docker compose up --wait` waits for running/healthy services; it is not a substitute for application health checks or smoke tests. Do not put a schema-dependent application health gate before the migration required to satisfy it. [8]
6. **Report the outcome.** Mark the exact revision ready only after checks pass. Publish authenticated preview links and record the commit, image references, definition revision, and result. Failures must remain visible; do not report success merely because containers started.

An existing preview retains its stable URLs and state while its application revision changes. An initial implementation may have brief update downtime: ordinary Compose recreation does not promise an atomic, zero-downtime release. Database migrations also mean restoring an old image is not automatically a safe rollback. Preserve state and diagnostics on failure instead of attempting destructive recovery.

## Cleanup and trust boundaries

Closing a PR or deleting a branch should trigger the configured cleanup policy. Deployment and teardown must share the same environment identity and lock. Re-check lifecycle state under the lock so a delayed build cannot recreate a closed preview.

Remove only resources recorded as belonging to that environment. Volume deletion must follow an explicit retention policy; never use broad Docker pruning as preview cleanup. A reopened PR may reuse retained state according to that policy. Quotas and a scheduled reconciliation/expiry pass should handle abandoned previews or missed events.

Use a dedicated staging host or appropriately isolated deployment targets, not a production host. Keep the database and SMTP endpoints internal and protect phpMyAdmin and Mailpit's web interfaces behind authentication or VPN access. Staging settings should use sandbox integrations; enforce network/egress restrictions where isolation matters rather than treating `APP_ENV=staging` as a security boundary.

Only explicitly trusted code may deploy to a shared Compose host. Branch-controlled Compose files and lifecycle hooks can execute code and request dangerous host access. Untrusted fork PRs require a separate isolated preview system or an explicit trust/approval policy, without exposing shared deployment secrets. Do not execute untrusted checkout code in a privileged `pull_request_target` workflow. Pin third-party CI actions and keep credentials scoped to the deployment task. [9]

## Initial acceptance criteria

The first implementation should demonstrate this with a small PHP/database fixture:

- Two feature branches run concurrently without container, URL, database, volume, or network collisions.
- phpMyAdmin connects only to its preview database and requires authentication; application test mail appears in that preview's Mailpit inbox.
- A new commit updates the same preview without changing its database credentials or losing previously seeded data.
- Missing configuration, failed builds, failed migrations, unhealthy applications, and conflicting inherited Compose settings fail visibly before a false ready status.
- Overlapping commits and cleanup cannot race into an outdated deployment or resurrect a closed preview.
- Cleanup follows the chosen retention policy and leaves other previews untouched.

A registry, staging host, ingress/TLS/authentication, secret storage, and application-specific hooks must be configured before a real deployment can be tested. This README does not provision those dependencies or claim these acceptance criteria have passed.
